# ADR-001. Выбор Apache Cassandra для истории операций склада

**Статус:** принято  **Вариант СРО:** 15

## Контекст
Журнал движений товаров (приход, расход, перемещение, корректировка) — append-only поток событий с высокой
интенсивностью записи. Чтение — по заранее известным шаблонам: «операции склада за день» и «история товара».

## Решение
Использовать Apache Cassandra с моделью «таблица под запрос» и **двумя таблицами**:
- `movements_by_warehouse_day` — PK `((warehouse_id, day), ts DESC, movement_id)`;
- `movements_by_product` — PK `((product_id, year_month), ts DESC, movement_id)`.
Запись в обе таблицы — LOGGED BATCH (атомарность между денормализованными копиями).

## Сравнение альтернатив
| Критерий | Cassandra | PostgreSQL | MongoDB | Redis |
|---|---|---|---|---|
| Масштабирование записи | линейное, мультимастер | вертикальное / сложное шардирование | шардирование, есть оверхед | ограничено RAM |
| Модель «время + ключ» | нативно (clustering order) | индекс по времени | индекс по времени | Streams/ZSET, но не как основное хранилище |
| Произвольные запросы/JOIN | нет | да | частично ($lookup) | нет |
| Долговечность журнала | высокая | высокая | высокая | зависит от персистентности |
| Вердикт | выбран | запасной вариант при малых объёмах | избыточно гибок | только для кэша |

## Последствия
- (+) Быстрые запросы по партиции, предсказуемая задержка, масштабируемость записи.
- (−) Дублирование данных (2 таблицы), нет JOIN и произвольных фильтров, агрегаты считаются в приложении.
- Контроль размера партиций: день для склада, месяц для товара (бакетирование); при росте — дробить на часы/недели.
- Hot partition: при очень интенсивном складе добавить `bucket` (например час) в partition key.
