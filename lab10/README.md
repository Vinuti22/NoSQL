## 1. Цель

Развернуть локальный MongoDB Replica Set из трёх узлов, записать данные с `w: "majority"`, контролируемо остановить primary, измерить время переключения (t1 − t0), вернуть узел, проверить потерю подтверждённых записей (RPO), сделать backup и восстановить его в отдельную базу.

Работа выполнена на собственном учебном стенде, только loopback `127.0.0.1`, только синтетические данные.

| 1 | 27102 | `data/rs2` | `<...>` | `<...>` |
| 2 | 27103 | `data/rs3` | `<...>` | `<...>` |

Replica Set: `rsLab10`, 3 голосующих узла, большинство = 2.

## 4. Выполнение (сценарий А — реальный Replica Set)

### 4.1 Запуск узлов
```bash
mongod --replSet rsLab10 --port 27101 --dbpath ./data/rs1 --bind_ip 127.0.0.1
mongod --replSet rsLab10 --port 27102 --dbpath ./data/rs2 --bind_ip 127.0.0.1
mongod --replSet rsLab10 --port 27103 --dbpath ./data/rs3 --bind_ip 127.0.0.1
```
(или `bash scripts/01_start.sh`)

### 4.2 Инициализация
```js
rs.initiate({_id:"rsLab10",members:[
  {_id:0,host:"127.0.0.1:27101"},{_id:1,host:"127.0.0.1:27102"},{_id:2,host:"127.0.0.1:27103"}]})
rs.status()
```
Скриншот: `screenshots/01_rs_status_before.png`

### 4.3 Тестовые данные
Коллекция `university_lab10.telemetry`: 30 документов (`eventId` 1–30, уникальный индекс), поля `vehicleId`, `ts`, `speedKmh`, `fuelPct`, `lat`, `lon`. Запись `insertMany(..., {writeConcern:{w:"majority", wtimeout:5000}})` — `scripts/03_seed.js`.
Количество документов: `<30>`. Скриншот: `screenshots/02_seed.png`

### 4.4 Моделирование отказа
Во время непрерывной записи (`scripts/04_writer.js`, каждое подтверждённое событие логируется) штатно остановлен только процесс текущего primary (порт `<...>`). Остальные узлы провели выборы.

### 4.5 Возврат узла
Остановленный `mongod` запущен повторно с теми же `dbpath`, портом и `replSet`; после синхронизации набор снова из трёх участников. Вернувшийся узел стал `<SECONDARY>` (автоматического возврата роли PRIMARY не предполагается).

### 4.6 Backup и восстановление
```bash
mongodump --uri="mongodb://127.0.0.1:27101,127.0.0.1:27102,127.0.0.1:27103/?replicaSet=rsLab10" --db=university_lab10 --out=./backup_lab10
mongorestore --uri="mongodb://127.0.0.1:27101,127.0.0.1:27102,127.0.0.1:27103/?replicaSet=rsLab10" --nsFrom="university_lab10.*" --nsTo="university_restore10.*" ./backup_lab10/university_lab10
```
Восстановление сделано в отдельную базу `university_restore10` без `--drop`; параллельных записей на момент дампа не было.

## 6. Анализ RPO и RTO

**Целевые значения (проектные допущения для телеметрии транспорта):** RPO ≤ 1 минута (допустима потеря последних точек трека: данные поступают часто и частично восстанавливаемы), RTO ≤ 1 минута (мониторинг в реальном времени, но не критичный по безопасности).

**Наблюдаемые:**
- RTO (t1 − t0) = `<... с>` → сравнить с целевым 60 с: `<укладывается / не укладывается>`.
- RPO: подтверждённых (ACK) записей `<N>`, найдено в БД `<N>`, потеряно `<0>`. Это означает отсутствие потери подтверждённых с `w:"majority"` записей **в данном прогоне**; успешный failover сам по себе RPO = 0 не доказывает. Записи с ошибкой (ERR) во время выборов клиентом не подтверждены и должны повторяться приложением.

**Ограничения эксперимента:** малая нагрузка, один компьютер, общий диск и процессор, нет сетевых задержек и разделов сети, одна попытка отказа. Результаты не переносятся на промышленную среду.

## 7. Выводы

- Репликация даёт доступность: при потере primary большинство (2 из 3) выбирает нового primary, записи с `w:"majority"` не теряются.
- Репликация не заменяет backup: ошибочное удаление или порча данных реплицируется на все узлы. Backup (`mongodump`) даёт копию на момент времени, которую проверили восстановлением в отдельную базу.
- `w:"majority"` гарантирует подтверждение большинством узлов, но не защищает от логических ошибок и потери всех узлов.
- Наблюдаемое время переключения: `<... с>`; потеря подтверждённых данных: `<0>`.

## 8. Ответы на контрольные вопросы

1. **Репликация и backup.** Репликация поддерживает копии на нескольких узлах для доступности и воспроизводит изменения (в т.ч. ошибочные); backup — отдельная копия на момент времени для восстановления.
2. **Кворум для выборов.** Нужно большинство голосов, чтобы два изолированных куска набора не избрали двух primary одновременно (split-brain).
3. **Роль primary.** Принимает обычные записи, пишет их в oplog; secondary воспроизводят oplog.
4. **Потеря большинства.** Нового primary не избрать; оставшиеся узлы становятся SECONDARY, запись недоступна, чтение возможно только при соответствующей read preference.
5. **`w:majority` и backup.** Он подтверждает запись большинством узлов, но удаление/порча данных тоже реплицируется; нужна независимая копия.
6. **Наблюдаемое время failover.** t1 − t0: от остановки primary до появления нового PRIMARY (секундомер, `rs.status()`, логи); дополнительно — пауза между ACK в `writer.log`.
7. **RPO/RTO.** RPO — допустимая потеря данных во времени; RTO — допустимое время восстановления работоспособности.
8. **Восстановление в отдельную базу.** Чтобы не перезаписать рабочие данные и безопасно сравнить количество и контрольные значения.
9. **Риски остановки primary.** Кратковременные ошибки записи, незавершённые операции, потеря неподтверждённых записей, при потере большинства — недоступность записи.
10. **Ограничения учебного стенда.** Один хост, малая нагрузка, нет сетевых сбоев, нет аутентификации и TLS, нет реального мониторинга и разнесения по зонам.
