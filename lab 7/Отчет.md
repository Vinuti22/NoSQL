## 2. Описание предметной области и пользователей

Предметная область **«Библиотека»** описывает взаимодействие читателей с книжным фондом, авторами литературных произведений и читательскими предпочтениями.

**Основные пользователи системы:**

1. **Читатели (Readers):** ищут книги для чтения, оформляют выдачу, интересуются определенными жанрами или авторами, получают рекомендации.
2. **Библиотекари / Администраторы:** управляют каталогом книг, фиксируют факты выдачи и возврата литературы, отслеживают популярность авторов.
3. **Аналитики:** исследуют паттерны чтения, популярность жанров и связь между интересами читателей и авторами книг.

## 4. Обоснование Neo4j и сравнение с документной моделью

Графовая модель (Property Graph) выбрана потому, что ключевые задачи библиотеки строятся на **глубоких связях между сущностями**: читатели берут книги, книги написаны авторами, а читатели имеют персональные интересы. Запросы поиска книг по общим авторам или цепочкам «читатель $\rightarrow$ книга $\rightarrow$ автор $\rightarrow$ другие книги» в реляционных БД требуют многократных соединений (`JOIN`), а в документных БД (например, MongoDB) — сложных денормализованных структур или агрегаций $lookup$. В Neo4j эти обходы выполняются естественно и эффективно с помощью визуальных шаблонов Cypher, так как связи хранятся как физические указатели (index-free adjacency).

## 5. Схема графа

* **Метки узлов (Labels):**
* `Reader` (свойства: `readerId`, `name`, `membershipCard`)
* `Book` (свойства: `bookId`, `title`, `genre`, `year`)
* `Author` (свойства: `authorId`, `name`, `country`)


* **Типы отношений (Relationships):**
* `[:BORROWED {date, status}]` — от `Reader` к `Book`
* `[:WroTE]` — от `Author` к `Book`
* `[:INTERESTED_IN]` — от `Reader` к `Book` (или жанру)


* **Пример пути:** `(:Reader {name: 'Алексей'})-[:BORROWED]->(:Book {title: 'Мастер и Маргарита'})<-[:WWROTE]-(:Author {name: 'Михаил Булгаков'})`

## 6. Cypher-команды создания данных (не менее 15 узлов и 20 отношений)

```cypher
// Создание авторов (3 узла)
MERGE (a1:Author {authorId: 101}) SET a1.name = 'Михаил Булгаков', a1.country = 'Россия';
MERGE (a2:Author {authorId: 102}) SET a2.name = 'Федор Достоевский', a2.country = 'Россия';
MERGE (a3:Author {authorId: 103}) SET a3.name = 'Эрих Мария Ремарк', a3.country = 'Германия';

// Создание книг (6 узлов)
MERGE (b1:Book {bookId: 201}) SET b1.title = 'Мастер и Маргарита', b1.genre = 'Роман', b1.year = 1967;

MERGE (b3:Book {bookId: 203}) SET b3.title = 'Преступление и наказание', b3.genre = 'Роман', b3.year = 1866;
MERGE (b4:Book {bookId: 204}) SET b4.title = 'Три товарища', b4.genre = 'Роман', b4.year = 1936;
MERGE (b5:Book {bookId: 205}) SET b5.title = 'На Западном фронте без перемен', b5.genre = 'Роман', b5.year = 1929;
MERGе (b6:Book {bookId: 206}) SET b6.title = 'Шерлок Холмс', b6.genre = 'Детектив', b6.year = 1892;

// Создание читателей (6 узлов)
MERGE (r1:Reader {readerId: 301}) SET r1.name = 'Денис Подгузов', r1.membershipCard = 'MC-001';
MERGE (r2:Reader {readerId: 302}) SET r2.name = 'Анелия', r2.membershipCard = 'MC-002';
MERGE (r3:Reader {readerId: 303}) SET r3.name = 'Тимур', r3.membershipCard = 'MC-003';
MERGе (r4:Reader {readerId: 304}) SET r4.name = 'Диас', r4.membershipCard = 'MC-004';
MERGE (r5:Reader {readerId: 305}) SET r5.name = 'Аружан', r5.membershipCard = 'MC-005';
MERGE (r6:Reader {readerId: 306}) SET r6.name = 'Карим', r6.membershipCard = 'MC-006';

// Создание связей WROTE (Автор - Книга) -> 6 отношений
MERGE (a1)-[:WROTE]->(b1)
MERGE (a1)-[:WROTE]->(b2)
MERGE (a2)-[:WROTE]->(b3)
MERGE (a3)-[:WROTE]->(b4)
MERGE (a3)-[:WROTE]->(b5)
MERGE (a4)-[:WROTE]->(b6);

// Создание связей BORROWED (Читатель - Книга) -> 9 отношений
MERGE (r1)-[:BORROWED {date: '2026-04-01', status: 'returned'}]->(b1)
MERGE (r1)-[:BORROWED {date: '2026-04-10', status: 'active'}]->(b4)
MERGE (r2)-[:BORROWED {date: '2026-03-15', status: 'returned'}]->(b1)
MERGE (r2)-[:BORROWED {date: '2026-04-05', status: 'active'}]->(b2)
MERGE (r3)-[:BORROWED {date: '2026-02-20', status: 'returned'}]->(b3)
MERGE (r4)-[:BORROWED {date: '2026-04-12', status: 'active'}]->(b6)
MERGE (r5)-[:BORROWED {date: '2026-01-10', status: 'returned'}]->(b5)
MERGE (r5)-[:BORROWED {date: '2026-04-14', status: 'active'}]->(b4)
MERGE (r6)-[:BORROWED {date: '2026-04-02', status: 'returned'}]->(b3);

// Создание связей INTERESTED_IN (Читатель - Книга/Интерес) -> 6 отношений
MERGE (r1)-[:INTERESTED_IN]->(b1)

MERGE (r2)-[:INTERESTED_IN]->(b2)
```

## 7. Реализация 7 запросов Cypher с пояснениями

### Запрос 1: Простое сопоставление (MATCH)

Получить список всех книг и написавших их авторов.

```cypher
MATCH (a:Author)-[:WROTE]->(b:Book)
RETURN a.name AS Author, b.title AS Book, b.genre AS Genre;

```

### Запрос 2: Фильтрация данных (WHERE)

Найти все книги жанра «Роман», изданные после 1930 года.

```cypher
MATCH (b:Book)
WHERE b.genre = 'Роман' AND b.year > 1930
RETURN b.title, b.year ORDER BY b.year ASC;

```

### Запрос 3: Сортировка и ограничение (ORDER BY / LIMIT)

Найти читателей, отсортировав их по имени, и вывести первые 3 записи.

```cypher
MATCH (r:Reader)
RETURN r.name, r.membershipCard
ORDER BY r.name ASC
LIMIT 3;

```

### Запрос 4: Запрос по направленному отношению

Найти все книги, которые взял конкретный читатель («Денис Подгузов»).

```cypher
MATCH (r:Reader {name: 'Денис Подгузов'})-[:BORROWED]->(b:Book)
RETURN b.title, b.genre, b.year;

```

### Запрос 5: Двухшаговый обход

Найти авторов, чьи книги брал читатель «Денис Подгузов» (путь: `Reader` $\rightarrow$ `Book` $\leftarrow$ `Author`).

```cypher
MATCH (r:Reader {name: 'Денис Подгузов'})-[:BORROWED]->(b:Book)<-[:WROTE]-(a:Author)
RETURN DISTINCT a.name AS Author, b.title AS BorrowedBook;

```

### Запрос 6: Обход переменной длины (Variable-length path, повышенное задание варианта)

Найти книги и других авторов, связанных через общих авторов или интересы читателя в пределах 2–3 переходов.

```cypher
MATCH (r:Reader {name: 'Денис Подгузов'})-[:BORROWED|INTERESTED_IN*1..2]->(b:Book)<-[:WROTE]-(a:Author)
RETURN DISTINCT a.name AS RelatedAuthor, b.title AS RecommendedBook;

```

### Запрос 7: Агрегирование (`count()`)

Подсчитать количество книг, взятых каждым читателем.

```cypher
MATCH (r:Reader)-[rel:BORROWED]->(b:Book)
RETURN r.name AS ReaderName, count(b) AS TotalBorrowed
ORDER BY TotalBorrowed DESC;

```

## 8. Изменение и безопасное удаление

* **Изменение свойства:** Обновим имя читателя или статус выданной книги.
```cypher
MATCH (r:Reader {readerId: 301})
SET r.name = 'Денис П. (Обновлено)'
RETURN r;

```


*Проверка изменения:* `MATCH (r:Reader {readerId: 301}) RETURN r.name;`
* **Безопасное удаление тестовой связи:**
1. Сначала выводим элемент для проверки с помощью `MATCH ... RETURN`:
```cypher
MATCH (r:Reader {readerId: 303})-[r_rel:BORROWED]->(b:Book)
RETURN r, r_rel, b;

```


2. Затем безопасно удаляем только выбранную связь:
```cypher
MATCH (r:Reader {readerId: 303})-[r_rel:BORROWED]->(b:Book)
DELETE r_rel;

```

## 9. Анализ преимуществ, ограничений и масштабирования

* **Эффективные запросы:** Запросы обхода графа (`MATCH` по связям `BORROWED`, `WROTE`) выполняются за $O(1)$ на каждый переход благодаря механизму *Index-Free Adjacency*, что значительно быстрее реляционных `JOIN` на больших глубинах.
* **Сложные запросы:** Неограниченные обходы переменной длины (`-*1..`) на миллиардных графах могут приводить к перегрузке памяти, поэтому обязательно ограничение глубины (например, `*1..3`).
* **Избыточные связи:** Прямые связи `INTERESTED_IN` дублируют часть информации `BORROWED`, но полезны для рекомендательных систем до фактической выдачи.
* **Сценарий роста графа:** При масштабировании базы данных (миллионы читателей и книг) Neo4j горизонтально масштабируется через кластеризацию (Causal Clustering), сохраняя высокую скорость поиска рекомендаций и путей.

## 10. Ответы на контрольные вопросы

1. **Что такое property graph?** — Это модель графа данных, состоящая из узлов (nodes), направленных отношений (relationships) между ними и свойств (properties, ключ-значение) у узлов и ребер.
2. **Чем узел отличается от отношения и свойства?** — Узел представляет сущность (объект), отношение соединяет два узла и имеет направление и тип, а свойство хранит конкретный атрибут (скалярное значение) узла или связи.
3. **Для чего используются labels в Neo4j?** — Метки (labels) группируют узлы по ролям или типам (например, `Reader`, `Book`), ускоряя поиск и индексацию.
4. **Чем CREATE отличается от MERGE?** — `CREATE` всегда создает новый элемент (создавая дубликаты, если шаблон уже есть), а `MERGE` ищет существующий шаблон и создает его только при отсутствии совпадений.
5. **Как MATCH описывает графовый шаблон?** — Он визуально изображает структуру с помощью круглых скобок для узлов и квадратных со стрелками для связей, например `(node1)-[:TYPE]->(node2)`.
6. **Почему направление отношения важно?** — Оно задает семантику предметной области (например, `Author` пишет книгу `WROTE` $\rightarrow$ `Book`, а не наоборот) и определяет направление обхода в запросах.
7. **Когда атрибут следует моделировать свойством, а когда отдельным узлом?** — Если атрибут простой и описывает только данный объект (например, год книги), он делается свойством. Если объект участвует в собственных связях и имеет множество атрибутов (например, автор), он выделяется в отдельный узел.
8. **Что показывает двухшаговый обход?** — Он позволяет найти связанные объекты через промежуточную сущность (например, читатель $\rightarrow$ книга $\rightarrow$ автор).
9. **Почему глубину variable-length path следует ограничивать?** — Во избежание комбинаторного взрыва и исчерпания ресурсов (памяти/процессора) при обходе плотных графов.
10. **Почему графовая модель может быть лучше документной для задач анализа связей?** — Документные БД хранят данные изолированно и требуют дорогих операций соединения или вложенных массивов ID, тогда как графовая БД оптимизирована под мгновенный переход по физическим указателям связей.
