## 3\. Объединение коллекций с помощью `$lookup`

```
db.patients.aggregate([
  {
    $match: {
      patientId: 101
    }
  },
  {
    $lookup: {
      from: "doctors",
      localField: "doctorIds",
      foreignField: "_id",
      as: "assigned_doctors"
    }
  }
])
```

# 6\. Сравнение моделей: Embedding vs Referencing

При проектировании связи **«Пациенты — Лечащие врачи»** можно использовать два подхода.

| Критерий | Embedding | Referencing |
| --- | --- | --- |
| **Дублирование данных** | Высокое: профиль врача дублируется у пациентов | Отсутствует: врач хранится один раз |
| **Удобство чтения** | Максимальное: данные доступны в одном документе | Требуется `$lookup` или несколько запросов |
| **Обновление данных** | Сложнее: необходимо изменять несколько документов | Проще: изменяется один документ врача |
| **Рост документов** | Возможен значительный рост документа | Хранятся компактные идентификаторы |
| **Сложность модели** | Простая | Более сложная |
| **Связи N:M** | Не всегда эффективно | Хорошо подходит |

## Вывод сравнения

**Embedding** предпочтителен, когда связанные данные:

- используются вместе;
- имеют небольшой размер;
- редко изменяются;
- имеют ограниченный рост.

**Referencing** предпочтителен, когда:

- данные являются общими для множества документов;
- существует связь `N:M`;
- связанные данные часто изменяются;
- список связанных элементов может значительно увеличиваться.

# 7\. Контрольные вопросы и ответы

## 1\. Что такое BSON?

**BSON (Binary JSON)** — бинарный формат представления документов, используемый MongoDB.

Он поддерживает дополнительные типы данных, которых нет в стандартном JSON, например:

- `ObjectId`;
- `Date`;
- `Int32`;
- `BinData`.

BSON оптимизирован для хранения и обработки документов MongoDB.

---

## 2\. Что такое Embedded Document?

**Embedded Document** — это вложенный документ, расположенный внутри другого документа в качестве значения одного из его полей.

Например:

```
{
  "name": "Екатерина Смирнова",
  "contact": {
    "phone": "+7-701-111-2233",
    "email": "example@mail.com"
  }
}
```

В данном примере `contact` является Embedded Document.

---

## 3\. Что такое Embedding?

**Embedding** — это способ моделирования данных MongoDB, при котором связанные данные хранятся непосредственно внутри одного документа.

Например:

```
patients
 └── contact
     ├── phone
     ├── email
     └── address
```

Преимущество такого подхода заключается в возможности получить связанные данные одним запросом.

---

## 4\. Что такое Referencing?

**Referencing** — это способ моделирования, при котором связанные сущности хранятся в разных коллекциях.

Связь между ними осуществляется посредством идентификаторов.

Например:

```
{
  patientId: 101,
  doctorIds: [201, 202]
}
```

При этом сами врачи находятся в отдельной коллекции `doctors`.

---

## 5\. Чем отличаются Embedding и Referencing?

| Embedding | Referencing |
| --- | --- |
| Данные находятся в одном документе | Данные находятся в разных коллекциях |
| Быстрое чтение | Может потребоваться `$lookup` |
| Возможна денормализация | Уменьшается дублирование |
| Подходит для небольших связанных данных | Подходит для общих и часто изменяемых данных |

**Embedding** обеспечивает удобство чтения, а **Referencing** помогает избежать дублирования данных.

---

## 6\. Что такое Dot Notation?

**Dot Notation** — это синтаксис обращения к полям вложенных документов и массивов.

Например:

```
db.patients.find({
  "contact.email": "smirnova.e@medtest.loc"
})
```

Здесь обращение к полю выполняется по пути:

```
contact → email
```

---

## 7\. Для чего нужны `$push` и `$all`?

### `$push`

Оператор `$push` добавляет новый элемент в конец массива.

```
db.patients.updateOne(
  { patientId: 101 },
  {
    $push: {
      allergies: "Latex"
    }
  }
)
```

### `$all`

Оператор `$all` используется для поиска документов, массив которых содержит **все указанные элементы**.

```
db.patients.find({
  allergies: {
    $all: ["Aspirin", "Dust"]
  }
})
```

---

## 8\. Что означают связи 1:1, 1:N, N:M?

### `1:1` — один к одному

Одной записи соответствует одна связанная запись.

**Пример:** пациент → паспортные данные.

### `1:N` — один ко многим

Одной записи соответствует несколько связанных записей.

**Пример:** пациент → история посещений.

### `N:M` — многие ко многим

Несколько записей одной сущности могут быть связаны с несколькими записями другой.

**Пример:** пациенты ↔ врачи.

---

## 9\. Почему опасны неограниченно растущие массивы?

Неограниченно растущие массивы могут привести к:

- увеличению размера документа;
- снижению производительности;
- проблемам при обновлении документа;
- достижению максимального размера документа MongoDB — **16 MB**.

Поэтому массивы следует использовать тогда, когда их размер остается разумно ограниченным.

---

## 10\. Что такое денормализация?

**Денормализация** — это намеренное дублирование или объединение данных для уменьшения количества запросов и ускорения чтения.

Например, некоторые данные врача можно сохранить непосредственно в документе пациента.

**Преимущество:** более быстрое чтение.

**Недостаток:** необходимость синхронного обновления дублирующихся данных.

---

## 11\. Когда использовать Embedding?

Embedding рекомендуется использовать, если:

- данные обычно считываются вместе;
- связь имеет тип `1:1`;
- связь имеет тип `1:N`;
- количество вложенных элементов ограничено;
- вложенные данные не требуют независимого управления.

**Пример:**

```
patient
 └── contact
```

---

## 12\. Когда использовать Referencing?

Referencing рекомендуется использовать:

- при связи `N:M`;
- при большом количестве связанных объектов;
- при часто изменяемых данных;
- когда связанные данные используются независимо;
- когда нежелательно дублирование информации.

В данной лабораторной работе Referencing применяется для связи пациентов и врачей.

---

## 13\. Для чего нужен `$lookup`?

`$lookup` используется внутри **aggregation pipeline** для объединения документов из разных коллекций.

Он выполняет операцию, аналогичную **Left Outer Join** в реляционных базах данных.

Пример:

```
{
  $lookup: {
    from: "doctors",
    localField: "doctorIds",
    foreignField: "_id",
    as: "assigned_doctors"
  }
}
```

В результате к документу пациента добавляется массив найденных врачей.

---

## 14\. Почему модель проектируют с учетом запросов?

MongoDB использует принцип **Query-Driven Data Modeling**.

При проектировании необходимо учитывать, каким образом приложение будет получать данные.

Вместо простого переноса реляционной схемы в MongoDB данные организуются таким образом, чтобы наиболее часто используемые данные можно было получить максимально эффективно.

Это позволяет:

- уменьшить количество запросов;
- ускорить чтение;
- правильно выбрать между Embedding и Referencing;
- оптимизировать структуру документов.
